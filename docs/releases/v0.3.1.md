# Cloister 0.3.1

Status: planned patch release; no `v0.3.1` tag or official `0.3.1` image has been
published. The checkout keeps package version `0.3.0` until release preparation.
The current published version is [0.3.0](v0.3.0.md).

## Project-specific workspace paths

Different projects previously shared Guest `/workspace`, so Agent session
history recorded the same working directory and resume pickers could mix
unrelated projects.

The selected canonical Host path now appears under Guest `/workspace`, and
the Agent starts at that exact mount target. For example:

```text
/Volumes/Projects/app -> /workspace/Volumes/Projects/app
```

Projects with the same directory name at different locations remain distinct.
Repeated launches and symbolic-link aliases of the same project use a stable
path. The rule applies to Codex, Claude, and explicit `--workspace` selection.
Only the selected project is mounted; its Host ancestors are not exposed.

Profile V7 and the shared Agent-state policy are unchanged. Project filtering
is an Agent feature, not a restriction on access to shared history. Codex users
can explicitly show all projects with `cloister codex -- resume --all`.

Existing sessions recorded at `/workspace` are left untouched and can be found
with `resume --all`. Moving a project changes its canonical path and therefore
its Guest working directory. The workspace remains a live read-write bind mount.

## Development validation on 2026-10-10

- `make verify` passed all 216 tests and Clippy.
- Regression tests cover namesake projects with shared state for both Agents,
  repeated launches, symbolic-link aliases, explicit workspace selection,
  Unicode names, spaces, literal shell characters, and resume argument forwarding.
- A real Apple container 1.5 smoke check verified a nested workspace path with
  Unicode and spaces, a read-only root, and Guest writes visible on the Host.
  Its temporary container was removed.
- The user tested the fix and reported no problems. This confirmation did not
  record exact Agent versions or a separate per-operation acceptance trace.

These checks validate development changes. Release-image, installation, and
Homebrew acceptance must be performed for the eventual 0.3.1 artifacts.
