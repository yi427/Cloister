# Cloister 0.2.0

Cloister 0.2.0 makes long-running Host Exec work easier to inspect and makes
the macOS CLI and Linux ARM64 Guest image an explicit, fail-closed release
pair. It keeps Profile V6 unchanged while adding an explicit upgrade path for
existing official release Profiles.

## Highlights

### Clear Guest workspace routing

The canonical Host Exec skill now tells Codex and Claude to read, write, list,
and patch `/workspace` with Guest file tools. `/workspace` is the live
read-write bind mount of the selected Host project; it is not a delayed or
separate copy.

Host Exec remains for Profile-allowed macOS executables. The skill explicitly
rejects Base64, Python, or another allowed interpreter as a workspace
file-transfer workaround, reducing unnecessary Host approvals and broad
interpreter use.

### Discoverable and waitable Host execution

`host.list_commands` now reports the fixed Host working directory used by
allowed commands, without adding a model-selected working directory or a
separate `pwd` capability.

`host.exec_status` accepts an optional `wait_ms`. A bounded wait returns when
new output arrives after the supplied cursor, the execution becomes terminal,
or the interval expires. Immediate status reads and cancellation remain
available, output cursors remain incremental, and status reads do not require
another execution approval.

### Exact CLI and image release pairing

Official `ghcr.io/yi427/cloister:X.Y.Z` images must exactly match the running
CLI version. Cloister rejects older, newer, moving, and unsupported official
references before Codex or Claude can create state, start the Host bridge, or
call Apple `container`; Agent `--dry-run` follows the same rule.

Full `sha-<40-hex>` tags remain available as immutable testing images with a
warning. Local and third-party images remain available with an explicit
unverified-compatibility warning. Official `main`, `latest`, and `X.Y` tags are
not valid persistent Profile references.

`cloister check` reports release compatibility separately from runtime image
availability. A paired release is `PASS`, a testing or custom image is `WARN`,
and an invalid official reference is `FAIL`.

### Explicit Profile image upgrade

After installing the 0.2.0 CLI, a Profile that selects the official 0.1.0 image
must be upgraded before launching an Agent:

```sh
cloister profile upgrade --dry-run
cloister profile upgrade
cloister check
```

The command upgrades only an older official exact-release image in a valid
current-schema Profile. Dry-run does not inspect or pull an image and does not
change files. The apply flow verifies the exact Linux ARM64 target, confirms
image pulling when needed, separately confirms the Profile edit, creates a new
owner-only backup, and atomically replaces only the TOML image value while
preserving comments, unrelated settings, and the original file mode.

Testing images, custom images, moving tags, future official images, symlink
Profiles, existing backup paths, and incompatible Profile schemas require
manual review.

## Installation

Cloister 0.2.x is distributed through the official Homebrew tap. The Formula
builds the CLI from the immutable release source and installs Apple `container`
as a runtime dependency. It does not start the runtime, create a Profile, pull
the Guest image, or rewrite an existing Profile.

```sh
brew install yi427/tap/cloister
```

Alternatively, compile directly from the exact Git tag:

```sh
cargo install --locked \
  --git https://github.com/yi427/Cloister.git \
  --tag v0.2.0 \
  cloister
```

The CLI and Guest image form one immutable release pair:

```text
CLI:   v0.2.0
Image: ghcr.io/yi427/cloister:0.2.0
```

The Linux ARM64 image pins:

| Tool | Version |
| --- | --- |
| Node.js | 24.19.0 |
| Rust | 1.97.1 |
| Codex | 0.147.0 |
| Claude Code | 2.1.227 |

## Security boundary

Cloister narrows ambient Host access but does not make every exposed
capability safe:

- `/workspace` is a live read-write bind mount. Guest writes, modifications,
  and deletions affect the selected Host project directly.
- Apple container's default network may reach the internet. A named or default
  network is not an egress firewall.
- Host Exec is an explicit escape hatch. An allowed executable runs with the
  macOS permissions and complete inherited environment of the user who
  started Cloister.
- Profile V6 still supports `arguments = "any"`; interpreters and build tools
  can therefore provide broad Host execution.
- Shared Agent-state directories contain credentials, settings, history, and
  sessions and must be treated as secrets.
- Approval prompts are interaction policy rather than a security boundary, and
  audit logs are observational rather than tamper-proof.

Cloister does not silently mount Host credential directories, existing Codex
or Claude directories, home directories, or privileged sockets.

Read the tagged
[security model](https://github.com/yi427/Cloister/blob/v0.2.0/README.md#security-model)
and
[architecture decisions](https://github.com/yi427/Cloister/tree/v0.2.0/docs/adr)
before enabling Host Exec for sensitive work.

## Requirements and known limitations

- Apple silicon Mac with Apple `container` 1.2 or newer.
- No Intel Mac, Linux-host, Docker, or general-purpose container-runtime
  support.
- No automatic Profile schema migration; 0.2.0 continues to use Profile V6.
- No automatic replacement of testing or custom images.
- No argument-level Host Exec restrictions beyond `arguments = "any"`.
- No Host-level CPU, memory, filesystem, or network containment for Host Exec.
- Running Host Exec jobs and captured output do not survive bridge shutdown.
- No GUI, prebuilt standalone CLI binary, or floating `latest` image tag.

## Release verification

The release procedure requires staged-snapshot and GitHub verification,
anonymous access to the exact Linux ARM64 image, installation from the
immutable `v0.2.0` tag, a real 0.1.0-to-0.2.0 Profile image upgrade, and smoke
tests for `init`, `check`, Codex, Claude, Host Exec discovery, bounded status
waiting, cancellation, and audit logging.

The exact release image and tag are immutable. A defective release is replaced
by a new patch version rather than by moving `v0.2.0` or its `0.2.0` image.
