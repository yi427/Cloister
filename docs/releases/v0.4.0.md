# Cloister 0.4.0

Release tag: `v0.4.0`. The matching base image is
`ghcr.io/yi427/cloister:0.4.0`.

This release adds explicit on-demand Host tools and Profile V8. Agents can
discover installed macOS commands and use them in the same conversation,
without editing the Profile or restarting the session for each command.
The default mode remains `allowlist`.

The base tool versions are unchanged:

| Base tool | Version |
| --- | --- |
| Node.js | 24.19.0 |
| Rust | 1.97.1 |

## On-demand Host tools

Create a separate Profile to deliberately enable broad Host access:

```sh
cloister init --host-exec-mode on-demand --profile /path/to/new-profile.toml
cloister codex --profile /path/to/new-profile.toml
# or: cloister claude --profile /path/to/new-profile.toml
```

Initialization discloses broad macOS-user authority before the normal Profile
creation confirmation. On-demand mode makes bare commands from the bridge's
startup PATH available without per-command registration or Cloister execution
prompts. Agent-client policies may still deny tools or request confirmation.

`host.list_commands` reports the selected mode and pinned commands.
The new read-only `host.find_command` checks one installed command without
executing it. Discovery is cached for the session, pinned commands take
precedence, and a changed canonical executable target requires rediscovery
after restarting the bridge. Relative and empty PATH entries are ignored.

Every on-demand `host.exec` requires a short `reason`. The canonical Host Skill
and MCP instructions guide both Agents to use Guest tools for routine workspace
work, explain Host operations, and reuse discovered commands. Execution still
uses literal arguments, bounded output/status polling, cancellation, and
metadata-only audit logs. Audit logs omit argument values, purpose text, and
environment values.

## Profile compatibility and upgrade

New Profiles use `schema_version = 8` and require explicit `host.exec.mode`:

```toml
[host.exec]
enabled = true
mode = "on-demand" # or "allowlist"
allow = []
```

Existing V7 Profiles remain supported with allowlist behavior. Installing the
CLI does not silently broaden their authority. After upgrading the CLI, update
the matching official image with:

```sh
cloister profile upgrade --dry-run
cloister profile upgrade
cloister check
```

`profile upgrade` changes only the official image reference and does not migrate
the schema or enable on-demand access. To enable the new mode, create a separate
V8 Profile or deliberately review a manual V8 configuration change. V6 and
earlier remain unsupported. Published 0.3.1 images lack the updated canonical
Host Skill and cannot be paired with the 0.4.0 CLI.

## Security boundary and validation

On-demand grants broad execution with the macOS user's permissions. Required
purpose text and Guest-first guidance influence Agent behavior; they do not
contain Host filesystem, network, shell, or interpreter access. Executables can
change at the same path, and discovery does not eliminate filesystem races.
The selected workspace remains a live read-write Host bind mount. Shared Agent
state remains separate Cloister-managed state; credentials and Agent software
are not baked into the base image.

Development checks passed all 229 tests and Clippy, including real authenticated
loopback MCP discovery, execution, purpose validation, status, cancellation,
audit redaction, V7/V8 parsing, and both Agent approval configurations. On
2026-10-11, the local development image passed Apple container 1.5 readiness
and actual Guest-to-Host connectivity checks; Codex 0.162.1 and Claude Code
2.1.296 were installed independently and passed executable launch checks.

Publication checks against the exact release image are recorded separately in
the [GitHub release](https://github.com/yi427/Cloister/releases/tag/v0.4.0).
Version output and deterministic configuration tests do not establish
authenticated model routing, Skill selection, or future Agent-client approval
behavior. Agent software continues to update independently of Cloister.
